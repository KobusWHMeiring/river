1. Philosophy & Meta-Level

Abseil Performance HintsProject Mycelium Alignment
“Choose the faster alternative if it does not impact readability significantly.”
Don’t defer all performance to later — pick the faster path at write-time when it’s free.		 ALIGNED Build Principles §4 (Pi Reality) mandates “Prefetch or Perish” — the faster QuerySet path is non-negotiable. §8.3 (Deletability/YAGNI) tempers this: “Build the simplest version.” The balance is right for our stack.
“Premature optimization is the root of all evil — but don’t pass up the critical 3%.”
Knuth, full quote. Focus on the 3% that matters.		 ALIGNED Meta-Principles: “Small Steps & Empirical Feedback” — build the minimal thing and iterate. The Pi Reality section explicitly targets the 3% that matters on constrained hardware.
Estimation: back-of-the-envelope math before coding.

3. Algorithmic Improvements

Abseil Performance HintsProject Mycelium Alignment
Turn O(N²) → O(N log N) or O(N). Avoid exponential behavior. IMPLICIT Health Audit Dimension B catches duplicated query patterns that are often the source of algorithmic waste (e.g., reconciled_payment_ids called 6 times). But we have no rule or scan that flags O(N²) patterns like nested loops over querysets. The Property Trap (§4) is an explicit algorithmic warning about N+1 via @property.
Replace sorted-list intersection (O(N log N)) with hash lookups (O(N)). COVERED BY DB Our “algorithm” layer is Postgres. Proper indexing + select_related/prefetch_related make this Postgres’s problem. ArchGuard RU-005 ensures we don’t revert to Python-side N+1.
Good hash functions so things are O(1) instead of O(N). N/A We use Postgres indexes (B-tree, GIN for JSONField), not in-process hash tables. This advice is C++ specific.

4. Memory Representation & Data Structures

Abseil Performance HintsProject Mycelium Alignment
Compact data structures — touching fewer cache lines. PARTIAL “Indices instead of pointers” maps to our UUIDs-as-FKs (fixed 16 bytes vs variable pointer). But we don’t think about Django model field ordering for cache-line effects. On a Pi with limited L2 cache, model field layout does matter for in-memory QuerySet evaluation. Not currently checked by any guard.
Memory layout: reorder fields, smaller numeric types, hot/cold separation. GAP Django abstracts memory layout away. However, JSONField blob size, queryset .only()/.defer() usage, and template context object size are our equivalents. No guard checks that views use .only() to limit field selection when rendering large lists.
Indices instead of pointers (32-bit indices into arrays). NATURAL FIT This is literally Django’s FK design. Our UUIDs are 128-bit (for sovereignty), but Postgres indexes them efficiently. The principle is already in the DNA of relational DB design.
Batched storage — avoid per-element allocation (std::map → flat_hash_map). COVERED BY DB Postgres stores rows contiguously in pages (8KB). Django’s prefetch_related does batched loading. This is a solved problem at the DB layer.
Inlined storage — InlinedVector for small collections. PARTIAL Our “inlined storage” equivalent is JSONField for small key-value data (Metadata Extensibility, §3). This is good. But we don’t have a pattern for “small list, don’t create a through-table.” The decision is ad-hoc per feature.
Unnecessarily nested maps — flatten to compound keys. NATURAL FIT Relational DB normalization handles this. Compound unique constraints are our “flattened map.” The EntityCategory boolean tags (§3) are an excellent example of flattening: instead of a nested mapping of entity→category→behavior, we use flat boolean fields.
Arenas — bulk-allocate, bulk-free. N/A Python’s GC and Django’s request-response cycle provide natural request-scoped arenas. No explicit arena pattern needed.
Arrays instead of maps / Bit vectors instead of sets. PARTIAL EntityCategory boolean tags (§3) are effectively a bit vector — excellent. But we could extend this pattern. E.g., a FarmEvent’s status field could use an integer bitmask instead of a CharField for fixed status sets, reducing index size on the Pi.

5. Reducing Allocations

Abseil Performance HintsProject Mycelium Alignment
Avoid unnecessary allocations.
Share static instances, stack-allocate, avoid heap.		 IMPLICIT Django’s request-scoped objects are our “allocations.” We avoid unnecessary queries via select_related (RU-005). But we don’t have patterns for sharing computed QuerySets across a request — multiple services may re-execute the same query within one HTTP request.
Resize/reserve containers. COVERED BY DB QuerySet is lazy and chunked. prefetch_related uses batched WHERE id IN (...) which is the DB equivalent of reserve. This is handled well.
Avoid copying — move, use pointers/indices. PARTIAL Django’s .values() and .values_list() avoid model instantiation overhead — but no guard checks that views use them for read-only list contexts. The Property Trap (§4) warns against per-instance QuerySet evaluation in loops. But we lack a scan for “view constructs full model instances when .values() would suffice.”
Reuse temporary objects — hoist outside loops. IMPLICIT The Property Trap rule (§4) is a specific case of this: don’t create a new query inside a loop. But we don’t have a general “hoist expensive calls out of loops” check. Health Audit Dimension B (duplicate query patterns) catches some of this.

6. Avoiding Unnecessary Work

Abseil Performance HintsProject Mycelium Alignment
Fast path for common cases. IMPLICIT “Success by Exception / Passive Routines” (§3) is our best example: assume success, only process failures. But we don’t systematically check for fast-path opportunities in service code. Health Audit Dimension B catches some via query duplication.
Precompute expensive information once. PARTIAL Category Behavior Tags (§3) are precomputed configuration — excellent. Django’s cached_property could be used more. But we have no guard checking whether computed properties re-evaluate unnecessarily.
Move expensive computations outside loops. ENFORCED RU-005 (prefetch) is exactly this: move the join to the DB, don’t loop in Python. Property Trap (§4) extends this to @property aggregations.
Defer expensive computation. IMPLICIT Django’s lazy QuerySets are the ultimate deferral mechanism. But we don’t enforce lazy evaluation patterns in service code. Some services might eagerly evaluate a QuerySet they don’t need.
Specialize code — write custom fast path instead of general library. CAUTION This conflicts with our DRY/Services-first philosophy. The Health Audit’s purpose is to reduce specialized duplication, not encourage it. Abseil’s advice applies to hot loops in C++ — our “hot loops” are SQL queries, where specialization means a custom query, not a custom algorithm. We already encourage .raw() or annotate-based queries for performance when needed.
Use caching to avoid repeated work. GAP Build Principles explicitly warn against caching: “Never cache data in Python application memory unless you have a bulletproof invalidation strategy.” (§7 DB SSOT). This is correct for financial/ecological data. But there’s a middle ground: cached_property on model instances within a single request, Django’s per-request cache, or template fragment caching. The gap is that we have no guidance on when request-scoped caching is safe vs. dangerous.
Make the compiler’s job easier — avoid function calls in hot paths, hand-unroll. N/A Python/C++ compiler advice doesn’t apply. Our equivalent is: make the QuerySet efficient (which RU-005 already enforces).
Reduce stats collection costs — sample, don’t collect for every event. ASPIRATIONAL We don’t collect runtime stats at all — this is a gap in the measurement domain (see §2), not a cost problem. If we add profiling, sampling should be the default approach.
Avoid logging on hot code paths. PARTIAL RU-010 catches print() but not excessive logger calls. The Abseil advice about precomputing VLOG_IS_ON outside loops maps to: check logger.isEnabledFor(logging.DEBUG) before building expensive log messages in loops. Not currently checked.

7. Code Size & Template/Inline Strategy

Abseil Performance HintsProject Mycelium Alignment
Trim commonly inlined code — move slow paths out of line. ENFORCED Build Principles §8.1: “No single file may exceed 30KB.” Health Audit Dimension A enforces >25KB warnings. This is our “inlining” equivalent: forced modularization prevents monolithic files. The Vertical Slicing mandate (§8.1) keeps files focused.
Inline with care — reduce icache pressure. ENFORCED “Thin Views” (§5) target <20 lines — the opposite of inlining. Services are the “out-of-line” code. This is good architecture and good performance hygiene for AI context windows.
Reduce template instantiations / Reduce container operations. N/A Python has no templates. The equivalent pattern (reducing duplicated QuerySet construction) is covered by Health Audit Dimension B.

8. API Design for Performance

Abseil Performance HintsProject Mycelium Alignment
Bulk APIs — reduce boundary crossings. PARTIAL Our “API boundary” is service method calls and DB queries. bulk_create / bulk_update exist in Django but no guard checks that services prefer them over per-instance .save() in loops. Health Audit Dimension B catches some duplicated query patterns but not bulk-vs-loop choice.
Organize code so performance improvements stay inside encapsulation boundaries. ENFORCED Boundary Separation (§2): logic in Services, not Views. Contract-First Design (§8.3): service signatures are the API. ArchGuard RU-002 (views touching DB) and RU-008 (cross-domain imports) enforce encapsulation.
Widely used APIs: be careful adding features — they constrain future implementations. ASPIRATIONAL Our Ubiquitous Language (§7) stops new top-level domain models. But we don’t have an “API deprecation” process. The Health Audit §8.4 gap (“Deprecation debt”) acknowledges this: old fields like settled_by linger. A pattern for marking service methods as deprecated would help.

9. Parallelization & Synchronization

Abseil Performance HintsProject Mycelium Alignment
Reduce lock contention, false sharing, use RCU. MOSTLY N/A Django’s process-per-request model avoids most in-process concurrency issues. The Pi runs few concurrent users. Postgres handles concurrent write safety via MVCC — we use select_for_update and transaction.atomic (RU-003) for the cases that need it.

10. Domain-Specific Advice (ProtoBuf / C++ / Pi)

Abseil Performance HintsProject Mycelium Alignment
Protocol Buffer advice: arena allocation, lazy parsing, string_view. N/A We use Django’s ORM + JSONField, not protos. Our equivalent optimization surface is: JSONField query patterns (GIN indexes), serializer efficiency (DRF SerializerMethodField cost), and template rendering cost.
C++-Specific: absl::flat_hash_map, InlinedVector, string_view, move semantics. N/A (LANGUAGE) Python equivalents: dict is already a hash table, list is a vector, string slicing creates copies (no string_view equivalent). The closest we get is using deque or array for fixed-size collections — not a current concern.
Bulk operations: process batches, not one-at-a-time. PARTIAL Covered in §8 (Bulk APIs). Our gap is that no guard checks for .save() inside a loop where bulk_create/bulk_update would be appropriate.

11. Gaps: What Neither System Currently Covers

These are areas where the Abseil hints don’t apply directly (different stack) and our Build Principles + Guards don’t address them — but the Pi context makes them important.

GapWhy Abseil Doesn’t Cover ItWhy It Matters for Us
JSONField blob size monitoring C++ structs are fixed-size; Abseil doesn’t deal with JSON blobs in DB columns. On the Pi, fetching a 50KB JSONField for every row in a 100-row QuerySet = 5MB of JSON deserialization. No guard checks .defer('large_json_field') usage in list views.
Template rendering cost No HTML rendering in C++ services. RU-009 catches nesting depth, but not: repeated template fragment evaluation, filter chain cost, or context object size. A 50-field model instance in context costs more to render than a flat dict.
Django signal chain length No signal/dispatch pattern. A single .save() can trigger 10+ signal handlers, each doing DB queries. No guard counts signal handlers per model or flags expensive signals.
Middleware stack depth No request middleware. Every request passes through all middleware. A slow middleware (e.g., one that hits the DB for user preferences) costs on every request. Not checked.
Asset bundle size (CSS/JS) C++ binaries — different concern. Total Isolation (§4) means all assets are local. CSS Alignment skill checks correctness, not bundle size. On a Pi serving over Wi-Fi, 500KB of CSS matters. Covered by PWA cache strategy (§4) for repeat visits, not first load.

12. Concrete Addition Suggestions

Based on the gaps identified above, here are actionable recommendations for new Build Principles, ArchGuard rules, and Health Audit dimensions. Grouped by effort and impact.

12A. Quick Wins (Low Effort, High Impact)

S1. ArchGuard RU-011: “.save() in a loop without bulk_create/bulk_update” HIGH PRIORITY

Abseil source: Bulk APIs (§8), Reduce allocations (§5 — avoid per-element ops).
What: Scan for for ... .save() patterns in service code (not views — those are RU-002). Flag if N > 1 saves could be bulk_create().
Why: On a Pi, 100 individual INSERTs is seconds of DB time vs. one bulk INSERT.
Effort: ~50 lines of AST pattern matching in scripts/archguard/rules/python_ast.py.

S2. Build Principle §4.6: “Use .only() and .defer() for list contexts” HIGH PRIORITY

Abseil source: Compact data structures (§4), Reduce allocations — avoid copying unnecessary data.
What: Add a principle: “When fetching QuerySets for list views (tables, dropdowns, card grids), use .only('field1', 'field2') to limit the columns fetched. For large JSONFields not needed in list context, use .defer('large_field').”
Why: Fetching all columns for a 100-row table on a Pi wastes memory and I/O. .only() tells Postgres to skip unneeded columns.
Effort: 3 lines in BUILD_PRINCIPLES.md, then a follow-up ArchGuard rule (RU-01X).

S3. Health Audit Dimension G: “.values() vs. model instantiation in read-only contexts” MEDIUM PRIORITY

Abseil source: Avoid copying (§5), Avoid unnecessary work (§6).
What: Scan views and services for QuerySets that are only used to build dicts/lists for JSON responses or templates. Flag if full model instances are constructed when .values() or .values_list() would suffice.
Why: Model instantiation is expensive (Django deserializes every field). For a read-only JSON endpoint returning 200 rows, .values() is 3-5× faster on a Pi.
Effort: Add one more grep/scan to the Health Audit checklist.

12B. Medium Investment

S4. ArchGuard RU-012: “Expensive log message construction in loops” MEDIUM PRIORITY

Abseil source: Avoid logging on hot code paths (§6), precompute VLOG_IS_ON outside loops.
What: Flag logger.debug(f”...”) or any log call with f-string/format inside a loop body, where the log level might be disabled at runtime.
Why: F-strings evaluate eagerly even if the logger discards the message. In a loop over 1000 items, that’s 1000 wasted string allocations.
Effort: ~40 lines AST pattern. Easier alternative: add a Build Principle (“check logger.isEnabledFor before expensive log formatting in loops”).

S5. Build Principle §4.7: “Request-scoped QuerySet reuse” MEDIUM PRIORITY

Abseil source: Reduce allocations — reuse temporary objects (§5), Use caching (§6).
What: If a QuerySet result is needed by multiple services within one HTTP request, the view or a request-scoped cache should materialize it once. Django’s QuerySets are lazy but not cached across different code paths.
Why: The Health Audit found _get_settled_ids() called 4× per dashboard load. A request-scoped functools.lru_cache or explicit materialization would fix this without violating the “no app-memory caching” rule (request scope is safe).
Effort: Add principle + pattern example. No automated guard needed (too hard to detect reliably).

S6. Performance regression test harness (minimum viable) MEDIUM PRIORITY

Abseil source: Measurement & profiling tools (§2), microbenchmarks.
What: Add a make perf-test target that runs key endpoints through pytest-django with django-querycount or django-perf-rec to assert query counts don’t regress. Start with the 5 most Pi-critical endpoints (dashboard, kanban, planner, rapid logger, cashbook).
Why: Static analysis can’t catch N+1 that arises from model __str__ methods, template tag calls, or DRF serializer depth. A query-count assertion (“dashboard loads in ≤ 8 queries”) makes performance a testable property.
Effort: ~2 days for initial harness + 5 endpoint tests.

12C. Nice to Have (Lower Priority / Exploratory)

S7. Build Principle §4.8: “Integer enums for fixed-choice fields” LOW PRIORITY

Abseil source: Enum values take up a whole word (§4), arrays instead of maps — bit vectors (§4).
What: For models with fixed, small choice sets (e.g., FarmEvent status with ≤ 16 values), prefer IntegerField with choices over CharField. The index and storage are smaller.
Why: On a Pi with limited RAM, smaller indexes mean more of the working set fits in Postgres shared buffers. This is a marginal gain — only worth it for high-row-count models.
Effort: 3 lines in BUILD_PRINCIPLES.md. No migration required for existing models unless they’re high-volume.

S8. Estimation checklist for new features LOW PRIORITY

Abseil source: Back-of-the-envelope estimation (§1).
What: Add a lightweight “Performance Estimate” section to the PRD template: “Expected row count, queries per request, JSON response size.”
Why: Catches design-level performance issues before implementation. E.g., a report that joins 5 tables with 10,000 rows each on the Pi needs a different approach than one with 50 rows.
Effort: Add to docs/engineering/PM_INSTRUCTIONS.md.

S9. Asset budget check (CSS/JS) LOW PRIORITY

Abseil source: Code size considerations (§7).
What: Add a simple script that checks total CSS/JS bundle size and warns if > 200KB (gzipped). Could be a CI check or a Health Audit dimension.
Why: Total Isolation means all assets are local. First load on a Pi over Wi-Fi is already slow. Keeping the bundle small prevents gradual bloat.
Effort: ~30 line shell script. Add to CSS Alignment skill as optional check.

The Big Picture

The Abseil Performance Hints and Project Mycelium’s quality stack come from different worlds (C++ systems programming vs. Django farm SaaS) but converge on the same truths: choose the faster path at write-time, encapsulate complexity, and enforce patterns mechanically.

Our Build Principles + ArchGuard + Health Audit stack already covers ~60% of what Abseil’s hints would translate to in a Django/Python context. The remaining 40% falls into two categories:

  • Runtime measurement (profiling, benchmarks, query-count assertions) — our biggest gap, and the one Abseil emphasizes most heavily.
  • Fine-grained ORM optimization (.only(), .defer(), bulk operations, values()) — uncovered because static analysis focuses on architecture, not query shape.

The 9 suggestions above close most of these gaps. Together with our existing stack, they create a performance discipline that spans the full spectrum: write-time principles → static enforcement → runtime measurement.
