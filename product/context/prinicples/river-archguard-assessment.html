2. What Is ArchGuard?

ArchGuard is Homtini's deterministic, AST-based static analysis engine that enforces Build Principles mechanically. It scans src/ Python files, templates, and CSS/JS using a plugin architecture of registered rules. Each rule is a standalone function decorated with @rule("RU-XXX", severity="ERROR"|"WARNING") that returns Violation objects.

Key insight: River's lint.py and Homtini's ArchGuard are complementary, not competing. lint.py catches semantic violations (business logic in wrong layer) that AST can't see. ArchGuard catches structural violations (missing prefetch, save-in-loop) deterministically. Together they'd give River defense-in-depth.

3. Rule-by-Rule Assessment

RuleSeverityDomainRiver StatusWhat It ChecksRiver Assessment
RU-001 ERROR Python PARTIAL Silenced exceptions — bare except: pass Build principles mandate it (§II: "Never use bare except: pass"), and lint.py prompts check for it. But there's no deterministic enforcement — AI-based lint could miss a bare except in unstaged code. Existing code should be scanned.
Risk: LOW — adding an AST scan is ~20 lines.
RU-002 WARNING Python FAILING Views touching Model.objects / .save() directly Major gap. River has only one service file (core/services/task_services.py). All 25+ views hit the DB directly via Task.objects.filter(), Section.objects.all(), etc. The build_principles.md §I says "Business logic must live in services/" but this is almost entirely unenforced. The ArchGuard rule has sophisticated exemptions (form.save(), serializer.save(), simple lookups, update_fields, setattr patterns).
Risk: HIGH — migrating views to services is a large refactor.
RU-003 WARNING Python PARTIAL Multiple DB writes without @transaction.atomic River's operations are mostly single-write (one form.save() per view). The task_services.py does have multi-write operations (creating task series) that should use atomic but don't. VisitLogCreateView.form_valid() saves a VisitLog + metrics + photos in one go without explicit atomic (Django's default per-request transaction partially covers this).
Risk: MEDIUM — adding atomic to existing multi-write paths is safe.
RU-004 WARNING Python N/A Bare .delete() — use soft-delete instead Homtini uses is_obsolete=True for immutable audit trails. River uses Django's DeleteView which does hard deletes. This is intentional for a small field-operations app — deleting a mistakenly created task is a valid operation, not an audit concern.
Verdict: Not applicable. Hard deletes are appropriate at River's scale.
RU-005 WARNING Python FAILING QuerySets missing .select_related() / .prefetch_related() Significant gap. The learnings document documents the need for select_related (MonthlyView implementation, §2 of learnings) and some views use it, but it's inconsistent. Many list views fetch sections/tasks without prefetching related fields. The build principles don't mention it. The ArchGuard rule is sophisticated — it:
  • Skips .all() on lookup tables
  • Skips chains ending in .values()/.exists()
  • Skips scalar-only filters (no __ joins)
  • Detects prefetch via variable reassignment

Risk: MEDIUM — adding prefetch is safe and improves performance.
RU-006 WARNING Python FAILING Service functions missing return type annotations Build principles mandate it (§II: "All Service functions must have Python type hints"). task_services.py has 3 functions — do they have type hints? The principle says they must, but there's no enforcement. River's views have no type hints at all (Django CBVs don't require them).
Risk: LOW — adding type hints is purely additive, zero behavioral risk.
RU-007 WARNING Template PARTIAL CDN references in templates Homtini's "Total Isolation" principle (Pi offline operation) mandates zero CDNs. River is a web app and deliberately uses CDN for Leaflet.js (mapping) and Material Symbols (icons). The icon font is already subsetted (~60KB). Leaflet is loaded from CDN — this is acceptable for a web app.
Verdict: Rule would flag Leaflet CDN. This is a false positive for River's context. If adopted, add a Leaflet exemption or change severity to INFO.
RU-008 WARNING Python N/A Cross-domain service imports River has one domain — a single core app. No cross-domain coupling possible. This rule would only become relevant if River grows to multiple Django apps.
Verdict: Not applicable at current scale.
RU-009 WARNING Template PARTIAL Template nesting depth > 2 River's templates have moderate nesting. The weekly/monthly planners have 3-4 levels in some areas (calendar grid inside day cells with Team/Manager splits). This rule would flag those.
Risk: MEDIUM — extracting partials could break the high-density layout that's core to the planner UX. Template restructuring needs visual QA.
RU-010 WARNING Python PARTIAL print() calls in production code lint.py catches this for staged changes. The learnings document shows debug prints were used and later removed (a healthy practice). Management commands use print legitimately.
Risk: LOW — scan is trivial to add. Management commands should be exempted (ArchGuard already skips management/commands/).
RU-011 ERROR Python PASSING Eager getattr() default evaluation This is a subtle N+1 trap: getattr(obj, 'cache', obj.expensive) evaluates obj.expensive eagerly even when cache exists. River's codebase is unlikely to hit this — it's a pattern Homtini discovered through real pain. Adding the scan is safe and costs nothing.
Verdict: Likely no violations, but check is cheap insurance.
RU-012 WARNING Python PASSING Model @property accesses relations not in view prefetch Sophisticated cross-analysis: scans model @property methods for related manager accesses, then checks view QuerySets for matching select_related/prefetch_related. River's models don't have @property methods that hit relations — they're data containers.
Verdict: No violations expected. Safe to add as a forward-looking guard.
RU-013 ERROR Python FAILING .save() / .create() inside loops #1 priority from Abseil analysis. River's task_services.py create_task_series() function loops over dates calling Task.objects.create() — this is exactly the pattern RU-013 catches. The rule has smart exemptions (transaction.atomic() wrap, form.save(), serializer.save(), service-named calls).
Risk: LOW-MEDIUM — changing to bulk_create is a mechanical refactor with clear performance upside and low behavioral risk.
RU-014 WARNING Python FAILING Expensive log formatting in loops Directly relevant to your logging goal. River has minimal logging infrastructure (settings.py has SENTRY_DSN but no structured logging config). This rule would catch f-string log calls inside loops — a pattern that should be guarded as logging is improved.
Risk: LOW — adding the scan is safe; actually improving logging infrastructure is a separate, larger task.
CSS-LAYOUT WARNING CSS N/A Layout utility classes defined in CSS Delegates to check_layout_utilities.py (Homtini-specific). River uses Tailwind via CDN, not custom CSS utilities. The check scripts don't exist.
Verdict: Not applicable. Replace with a Tailwind-specific check if needed.
CSS-CLASSES WARNING CSS N/A CSS class naming conventions Delegates to check_css_classes.py (Homtini-specific). River uses Tailwind utility classes.
Verdict: Not applicable.
CSS-JS-* WARNING CSS/JS N/A Delegated CSS/JS checker fallback Fallback when delegated checker scripts are missing.
Verdict: Not applicable.

4. Gap Analysis: What River Lacks vs. ArchGuard

Beyond individual rules, there are structural gaps between River's current quality tooling and ArchGuard:

CapabilityRiver Has It?Gap Description
Rule registry + discovery ❌ No plugin architecture. lint.py is a monolithic prompt-based checker.
Deterministic AST scanning ❌ Only AI-based lint. No Python AST walker for structural patterns.
Template scanning ❌ No regex-based template linting (nesting depth, CDN checks).
Per-phase audit trail ❌ No docs/audits/ directory. No phase-gated enforcement.
Violation data model ❌ No structured violation type — lint.py outputs raw AI text.
Self-testing rules ❌ AI-based lint can't be unit-tested. ArchGuard rules each have temp-project tests.
CI-compatible exit codes ✅ lint.py exits 0/1 based on AI response. ArchGuard also exits 0/1.
Configurable severity ❌ Each ArchGuard rule declares ERROR vs WARNING. lint.py has no tiering.
Directory exclusions ✅ (implicit) lint.py only scans git staged changes. ArchGuard has explicit skip lists.

5. Prioritized Action Plan

Actions ordered by impact × urgency ÷ effort. Each references the relevant Abseil insight (from the comparison analysis) and the ArchGuard rule it maps to.

P0 — NOW Add Missing Build Principles

Effort: 15 min  |  Risk: Zero (documentation only)

Add a new §VI "Performance Patterns" section to build_principles.md covering:

  • Bulk Over Loop — Never .save() in a loop (→ RU-013, Abseil S1)
  • Fetch Only What You Need — Use .only()/.defer() for list contexts (→ Abseil S2)
  • Flat Over Fat for Rendering — Prefer .values() for read-only (→ Abseil S3)
  • Guard Log Calls in Loops — Check logger.isEnabledFor() before f-string formatting (→ RU-014, Abseil S4)
  • Precompute Once, Use Many — Compute at view level, pass via context (→ Abseil S5)
  • Always Prefetch Relations — .select_related() for FK, .prefetch_related() for M2M/reverse FK in every list view (→ RU-005)

Effort: 30 min  |  Risk: Low

The one confirmed RU-013 violation: core/services/task_services.py loops over dates calling Task.objects.create(). Replace with Task.objects.bulk_create([...]). This is the #1 Abseil-recommended fix and directly improves DB performance.

Effort: 20 min  |  Risk: Low

Audit create_task_series() and VisitLogCreateView.form_valid() for multi-write paths lacking explicit atomicity. Add @transaction.atomic decorator or with transaction.atomic(): blocks. This prevents partial writes on failure (→ RU-003).

6. Risk Assessment per Refactor Category

6A. Adding Build Principles (Documentation)

Risk: NEGLIGIBLE. Documentation changes have zero behavioral impact. The only "risk" is the principles becoming aspirational rather than enforced — mitigate by adding ArchGuard rules in the next sprint.

6B. Adding .select_related() / .prefetch_related()

Risk: VERY LOW. Adding prefetch is a pure performance optimization. It doesn't change query results, only how they're fetched. The main risks are:
  • Over-fetching: .select_related() JOINs all specified tables. On models with many FK fields, pick only the ones actually used in the template.
  • Template breakage: If a template accesses {{ task.section.name }} but section isn't prefetched, it still works (Django lazy-loads). Prefetch just makes it faster. No template breakage possible.

6C. Replacing .save() in Loops with bulk_create()

Risk: LOW-MEDIUM. bulk_create() has different semantics from .save() in a loop:
  • No .save() hooks: bulk_create() doesn't call Model.save(), signals (post_save), or clean(). If River has signal handlers or custom save() logic on Task, these won't fire.
  • No auto-now fields: auto_now_add works, but auto_now does not get updated per-object with bulk_create.
  • No PK assignment in SQLite: SQLite with bulk_create doesn't set PKs on returned objects unless the model has a single AutoField.
  • Mitigation: Audit Task model for signal handlers and custom save() logic before making the switch. If signals are critical, use bulk_create + manually trigger signals, or wrap in transaction.atomic instead.

6D. Adding @transaction.atomic

Risk: LOW. Adding atomicity is strictly correctness-preserving:
  • The existing code without atomic can partially fail (some writes succeed, some don't).
  • Adding atomic ensures all-or-nothing — strictly better.
  • The only risk is nested atomic blocks (Django uses savepoints, which have minor overhead). Don't wrap an already-atomic view in another atomic decorator.

6E. Setting Up Structured Logging

Risk: LOW-MEDIUM. Logging is additive — it doesn't change behavior. Risks are:
  • Disk I/O on Pi-like hardware: Not applicable (River runs on a standard server). File-based logging with rotation is safe.
  • Sensitive data leakage: Ensure log messages don't include user data, passwords, or PII. Add a log sanitizer or use Sentry's PII scrubbing.
  • Sentry quota: If using Sentry's free tier, verbose logging could exhaust the event budget. Sample errors at an appropriate rate.

6F. Adapting ArchGuard for River

Risk: MEDIUM. Adapting static analysis infrastructure requires care:
  • False positives: Rules written for Homtini's patterns may flag legitimate River patterns. The RU-002 exemptions (form.save(), setattr patterns) need tuning for River's class-based-view style.
  • CI gate friction: If ArchGuard exits 1 on ERROR, devs can't commit until violations are fixed. This gates feature work. Start with all rules as WARNING, then escalate to ERROR once the codebase is clean.
  • Directory structure mismatch: ArchGuard expects src/ with src/core/views/, src/core/services/. River uses flat core/views.py, core/services/task_services.py. The path checks (_is_in_views, _is_in_services) need updating.
  • Mitigation: Run ArchGuard in advisory mode (WARNING-only, exit 0) for the first sprint while tuning exemptions. Then promote to gating.

6G. Migrating Views to Services (RU-002)

Risk: HIGH. This is the largest refactor. River's 25+ CBVs directly access the ORM. Moving query logic to services would touch every view:
  • Regression risk: Every view touched is a potential regression. River's test coverage is incomplete (5 test files, mostly planner/dashboard). Need to add tests before refactoring.
  • Scope creep: A "move everything to services" refactor could take a full sprint and block feature work.
  • Limited benefit at current scale: At ~25 views in a single app, the service layer abstraction adds indirection without the multi-domain coupling it prevents in Homtini.
  • Recommendation: Don't migrate existing views. Apply the service-layer rule to new code only. Existing views are stable. The principle is prophylactic, not curative — enforce on new features, don't rewrite working code.

7. Summary & Recommendations

What To Do This Sprint

  1. Update build_principles.md — add §VI Performance Patterns (bulk-over-loop, only/defer, values-over-model, log-guard, precompute-once, always-prefetch). 15 minutes. Zero risk.
  2. Fix create_task_series() — replace .save() in loop with bulk_create(). Add @transaction.atomic. 30 minutes. Low risk.
  3. Add .select_related() to list views — systematic audit of views displaying FK-related data. 1–2 hours. Very low risk.
  4. Add type hints to task_services.py — compliance with existing build principle. 15 minutes. Zero risk.
  5. Set up structured logging — LOGGING dict, Sentry integration, request IDs. 2–3 hours. Low risk.
  6. Regenerate CURRENT_STATE.md — run python summarise.py. 1 minute. Zero risk.

What To Do Next Sprint

  1. Adapt ArchGuard for River — clone engine, update paths, tune exemptions, run in WARNING-only advisory mode. 4–6 hours. Medium risk (manageable with advisory mode).
  2. Add query-count regression tests — top 5 endpoints. 1–2 days. Low risk.

What NOT To Do (Yet)

  • ❌ Don't migrate existing views to services. Too high risk for too little benefit at current scale. Enforce on new code. Consider extracting shared query patterns (e.g., "get tasks for date range with sections") to service functions without touching views.
  • ❌ Don't add soft-deletes (RU-004). Hard deletes are appropriate for River's domain. Don't add complexity you don't need.
  • ❌ Don't remove Leaflet CDN (RU-007). Mapping is a core feature. Self-hosting Leaflet adds maintenance burden with no user-facing benefit for a web app.
  • ❌ Don't extract planner partials (RU-009) without visual QA. The high-density calendar grid is sensitive. Wait until you have Playwright E2E tests to catch regressions.

The Big Picture

River's build principles are good but unenforced. The ArchGuard code sitting in product/context/prinicples/archguard/ is a working, tested engine that can close that gap. The adaptation cost is low (~half a day) and the payoff — deterministic, CI-gated enforcement of every principle — is high.

The priority order is: document principles → fix known violations → add enforcement → add measurement. This creates a quality stack that Homtini has proven works: write-time principles → static enforcement → runtime measurement. Start with P0 actions this sprint, and you'll have a dramatically stronger foundation before adding any new features.
